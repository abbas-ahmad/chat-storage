# Distributed Tracing and Audit Logging

This document explains the distributed tracing and audit logging implementation in the Chat Storage service.

## Overview

The application implements comprehensive request/response logging with distributed tracing support using:
- **Micrometer Tracing** with Brave for trace context propagation
- **MDC (Mapped Diagnostic Context)** for correlation IDs
- **Custom RequestResponseLoggingFilter** for audit trails
- **Zipkin** (optional, disabled by default) for trace visualization

**Note:** Zipkin dependency is commented out by default. The tracing functionality (trace/span IDs) works without Zipkin. Uncomment the Zipkin dependency in `pom.xml` only if you want to export traces to a Zipkin server.

## Features

### 1. Distributed Tracing
Every request is automatically assigned:
- **Trace ID**: Unique identifier for the entire request flow across services
- **Span ID**: Unique identifier for this specific service's processing

These IDs are:
- Automatically generated by Micrometer Tracing
- Propagated in HTTP headers for distributed systems
- Included in all log entries via MDC

### 2. Request/Response Audit Logging
All API requests and responses are logged with:
- Full request details (method, URI, headers, body)
- Full response details (status, headers, body)
- Trace and Span IDs for correlation
- Request duration in milliseconds
- User identification (X-User-ID header)
- Automatic masking of sensitive headers (X-API-KEY, Authorization)

### 3. Structured Logging
Logs are written in a structured format with:
- Timestamp
- Thread name
- Trace ID and Span ID
- Log level
- Logger name
- Message


## How It Works

### 1. RequestResponseLoggingFilter
Located at: `src/main/java/store/chat_storage/filter/RequestResponseLoggingFilter.java`

This filter:
- Runs early in the filter chain (`@Order(Ordered.HIGHEST_PRECEDENCE + 1)`)
- Wraps request/response to cache content for logging
- Extracts trace context from Micrometer Tracer
- Adds trace IDs to MDC for automatic inclusion in logs
- Logs request before processing
- Logs response after processing with duration
- Automatically masks sensitive headers

**Excluded Endpoints:**
- `/actuator/**` - Health and metrics endpoints
- `/swagger-ui/**` - Swagger UI
- `/v3/api-docs/**` - OpenAPI documentation

### 2. Trace Context Propagation
- Micrometer Tracing automatically creates spans for web requests
- Trace context is propagated in HTTP headers:
  - `traceparent` - W3C Trace Context header
  - `b3` - Zipkin B3 format (if configured)
- Context is available throughout the request lifecycle

### 3. MDC Integration
The filter adds to MDC:
```java
MDC.put("traceId", traceId);
MDC.put("spanId", spanId);
```

These are automatically included in log patterns via `%X{traceId}` and `%X{spanId}`.

## Usage in Distributed Systems

### Trace Propagation
When this service calls other services, include the trace headers:

```java
HttpHeaders headers = new HttpHeaders();
Span currentSpan = tracer.currentSpan();
if (currentSpan != null) {
    headers.add("traceparent", generateTraceParentHeader(currentSpan));
}
```

### Searching Logs by Trace ID
To find all logs for a specific request:
```bash
grep "traceId=64d8e8c8f8b3a1b2" application.log
```

## Optional: Zipkin Integration

**By default, Zipkin is disabled.** The application still provides full tracing with trace/span IDs in logs without Zipkin.

To enable Zipkin for trace visualization:

### 1. Uncomment Zipkin Dependency in pom.xml
```xml
<!-- Zipkin reporter (optional - uncomment if you want to export traces to Zipkin) -->
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>
```

### 2. Uncomment Zipkin Configuration in application.yaml
```yaml
management:
  zipkin:
    tracing:
      endpoint: ${ZIPKIN_ENDPOINT:http://localhost:9411/api/v2/spans}
```

### 3. Rebuild the Application
```bash
mvn clean package
```

### 4. Run Zipkin Locally
```bash
docker run -d -p 9411:9411 openzipkin/zipkin
```

### 5. View Traces
Open browser: http://localhost:9411

## Production Recommendations

### 1. Adjust Sampling Rate
For high-traffic production systems:
```yaml
management:
  tracing:
    sampling:
      probability: 0.1  # Sample 10% of requests
```

### 2. Body Logging
Consider disabling or limiting body logging for:
- Large payloads (currently limited to 10KB)
- Sensitive data endpoints
- High-traffic endpoints

Modify `RequestResponseLoggingFilter` to exclude specific paths:
```java
if (requestUri.startsWith("/api/v1/sensitive")) {
    requestLog.put("body", "[REDACTED]");
}
```

### 3. Log Aggregation
Use a centralized logging solution:
- ELK Stack (Elasticsearch, Logstash, Kibana)
- Splunk
- CloudWatch Logs
- Datadog

### 4. Sensitive Data Masking
Current implementation masks:
- `X-API-KEY` header
- `Authorization` header

Add more fields as needed in the filter.

## Performance Considerations

### Filter Impact
- **Request/Response Wrapping**: Minimal overhead (~1-2ms)
- **Logging**: Asynchronous logging recommended for production
- **Trace Context**: Negligible overhead
- **Body Caching**: Limited to 10KB to prevent memory issues

### Optimization
For async logging, add to `application.yaml`:
```yaml
logging:
  pattern:
    console: "%d{yyyy-MM-dd HH:mm:ss} [%thread] [%X{traceId},%X{spanId}] %-5level %logger{36} - %msg%n"
  async:
    queue-size: 256
    discarding-threshold: 0
```

## Troubleshooting

### No Trace IDs in Logs
- Verify Micrometer Tracing dependencies are included
- Check that `management.tracing.sampling.probability` > 0
- Ensure logging pattern includes `%X{traceId}` and `%X{spanId}`

### Filter Not Running
- Verify `@Component` annotation is present
- Check that filter is not excluded by configuration
- Verify `@Order` annotation for correct execution order

### Large Memory Usage
- Reduce body logging size limit in filter
- Exclude high-traffic endpoints from audit logging
- Implement request/response size limits

## Security Considerations

1. **Sensitive Data**: Always mask sensitive headers and body fields
2. **Log Storage**: Ensure logs are stored securely with proper access controls
3. **Data Retention**: Implement log rotation and retention policies
4. **Compliance**: Ensure logging complies with GDPR, HIPAA, or other regulations
5. **PII**: Avoid logging personally identifiable information
